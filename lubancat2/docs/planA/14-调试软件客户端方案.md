# 14 调试软件客户端方案（VSCodium / DAP）

> 定位：`13-调试通道与上位机通讯.md` 定的是**控制器侧**的调试口（C++ `DebugServer`）；
> 本文定的是**PC 侧客户端**用什么基座、怎么接。两者是同一件事的两端。
> 本文为**方案整理，尚未实施**（无插件、无 Debug Adapter 代码）。
>
> 前提：客户端技术栈在既有文档中**从未涉及**——`08` §8 明确把「脚本编辑器 / 断点单步 / 变量窗口」
> 这类 UI 划在「调试软件自行实现」（`08` §6 末、§4.3），本项目此前只承诺提供**后端**。
> 本文即回答「这个调试软件用什么做」。

---

## 1. 结论先说

| 问题 | 结论 |
|------|------|
| 基于 VSCodium 开发好不好？ | **好**，是投入产出比最高的路径 |
| 做插件还是做发行版？ | **先做插件**（Extension），交付现场时再做**定制 VSCodium 发行版**（把插件内置） |
| 从零自研 UI（Qt/Web）？ | **不推荐**（成本极高，除非有硬性需求） |
| 要不要上 Eclipse Theia？ | 仅在要做成「自家独立 IDE 品牌」时考虑，非必要 |

一句话：**VSCodium + 自研 Debug Adapter（走 DAP）**，UI 基本白送，我们只写「协议翻译层」。

---

## 2. 为什么它和本项目天然咬合

### 2.1 位置：客户端在 PC，不在控制器

```
VSCodium (PC)  ──DAP/stdio──▶  kinex-debug-adapter (PC)  ──JSON-Lines/TCP──▶  控制器 DebugServer（见 13）
   └ 断点/变量/调用栈/终端 UI   └ 只做协议翻译（任意语言可写）      └ 只读 Shared 快照、与 RT 隔离
```

- ⚠️ **不要把 VS Code Server 装在控制器上**：RK3568 是精简系统，Node 常驻不合算；
  控制器只暴露 `13` 的 JSON-Lines 调试口。
- Adapter 走 stdio 与 IDE 通讯、再走 TCP 连控制器（两跳），这是 DAP 的标准形态（gdb/lldb adapter 亦然）。

### 2.2 关键：`IScriptEngine` 早已按「调试软件后端」设计

`08` 已明确把调试所需接口备好，且**无需改动内核与 RT 线程**：

```459:460:lubancat2/docs/planA/08-ZBasic脚本引擎.md
后续若调试软件要做「脚本编辑器 + 断点/单步 + 变量窗口」，可直接复用本引擎的
`compile/run/request_abort/status/get_var/set_var/labels/set_trace` 接口，无需改动内核与 RT 线程。
```

这套接口**几乎就是 DAP 的语义**（`09` §3.8 也把它描述为「统一调试入口」「便于统一 UI」）。

### 2.3 DAP ↔ 现有接口映射（近乎 1:1）

| DAP 请求 | 对接现有接口 / `13` 的 RPC |
|----------|-----------------------------|
| `initialize` / `configurationDone` | `sys.info` / `script.run` |
| `setBreakpoints` | `labels()`（BASIC）／ 行号表（Lua） |
| `stackTrace` | 当前行；BASIC 的 `GOSUB/SUB` 链，Lua 有真实调用栈 |
| `scopes` / `variables` | `list_vars()` / `get_var()` |
| `setVariable` | `set_var()` |
| `evaluate`（REPL / 监视） | 表达式求值 + `MotionHost::call()` 执行命令 |
| `next` / `stepIn` / `stepOut` / `continue` | 需**引擎 pause 钩子**（`13` §5.2） |
| `output` 事件 | `print()` 落点 / `log` 订阅 |
| 终止原因（terminate / exception） | `Status`：`DONE` / `RUNTIME_ERROR` / `ABORTED` / `BUDGET_EXCEEDED` |

| 引擎 `Status` | DAP 终止语义 |
|----------------|---------------|
| `READY` | 运行中（`continued` 事件） |
| `DONE` | 正常结束（`exited`，code 0） |
| `COMPILE_ERROR` / `RUNTIME_ERROR` | `stopped`(exception) + `error_line` 定位 |
| `ABORTED` | 用户停止 |
| `BUDGET_EXCEEDED` | `stopped`(error)，附 `steps` 供诊断 |

> 也就是说：`status` / `error_line` / `steps` / `labels` / `set_trace` 这些本就为统一 UI 而生，**接 DAP 属于顺水推舟**。

## 3. 三种形态对比

"基于 VSCodium 开发"与"做个插件"其实是**两个层次**，后者天然向上兼容前者：

| 形态 | 成本 | 定制力 | 适用场景 |
|------|------|--------|----------|
| **A. 插件（Extension）** | 最低 | 中（受 VS Code UI 约束） | **首选起点**；产出 `.vsix`，装官方 VS Code 也能用 |
| **B. 定制 VSCodium 发行版** | 中 | 高（品牌、预置插件、默认配置、一键连接、锁设置） | 交付现场「开箱即用」；可再分发 |
| **C. Eclipse Theia** | 中高 | 很高（VS Code 技术栈，专为自造 IDE 而设） | 要做成「自家 IDE 产品」品牌时 |
| ~~D. 从零自研 UI（Qt/Web）~~ | 极高 | 极高 | **不推荐**，除非有硬性需求 |

**推荐路线**：**A 起步 → B 收尾**；C 仅在确有品牌化诉求时再评估。

## 4. 插件功能清单：白送的 vs 要自研的

| VS Code / VSCodium 白送（零成本） | 需要自研 |
|-----------------------------------|----------|
| 脚本编辑器、多文件、Git、SSH Remote | **Debug Adapter**（DAP ↔ `13` 的 JSON-Lines） |
| 断点 / 变量 / 监视 / 调用栈 / 步进 UI | TextMate 语法高亮（`.tmLanguage.json`，很轻） |
| 输出面板、Problems、集成终端、REPL 面板 | 状态面板（轴/总线/4x 寄存器）→ 树视图或 Webview |
| 设置页、快捷键、主题、跨平台打包 | **实时曲线/示波器** → 自定义 Webview + `13` 的事件订阅 |
| 命令面板、Workspace 管理 | 设备命令补全（数据源：`command_table.h` / `motion_host.h`） |

> 「在线编程/下载/参数配置」用 **VS Code Command + `13` 的 RPC** 实现即可；
> 若要做语言级智能（补全、诊断、跳转），再补一个 **LSP**（见 §6.4）。

## 5. 需要与 `13` 联动的部分

| 客户端功能 | 依赖 `13` 的哪个阶段 |
|------------|----------------------|
| 连接 / 运行 / 停止 / 输出 | D1~D2（通道 + `script.*`） |
| 断点 / 单步 / 变量 / 监视 | D4~D5（**热更新 + 引擎 pause 钩子**） |
| 状态面板 / 寄存器表 / 曲线 | D3（订阅推送） |
| 波形/高频采样 | 若需要，按 `13` §9 单独设计高频通道 |

> 结论：客户端的完整度**受限于 `13` 的引擎侧改动**（D4/D5），不是插件本身的工作量。

## 6. 风险与注意（真坑）

1. **Marketplace 限制**：VSCodium 默认用 **Open VSX**，不是微软 Marketplace。
   自研插件无影响；若依赖第三方插件，须先确认 Open VSX 有替代。
2. **许可证**：VS Code **官方二进制不可再分发**——要做发行版只能用 **VSCodium / Code-OSS 源码构建**
   （这正是 VSCodium 存在的意义）。自研插件本身无此约束。
3. **DAP 不覆盖实时曲线**：波形要单独设计（自定义 Webview + 事件订阅，或参考 UR 把高频数据流单独开一条通道）。
   别指望 DAP 解决。
4. **BASIC 没有现成的 LSP/DAP**：全自研，但工作量可控（引擎已备好）。
   **轻量替代**：第一版只上 TextMate 语法 + 复用引擎 `compile` 的报错做诊断，暂不写 LSP。
5. **Adapter 语言自由**：只有 UI 部分必须 JS/TS；Debug Adapter 走 stdio，可用 C++/Python/Go 写。
6. **学习曲线**：现场工程师从 ZDevelop 式界面迁到 VS Code 式界面需适应期；
   可用 B 形态（预置配置 + 精简菜单 + 一键连接）缓解。
7. **版本演进**：DAP / VS Code Extension API 相对稳定，但仍需跟随升级，避免长期锁死旧版本。
